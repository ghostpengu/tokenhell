# Cursor event costs and token semantics

Research date: 2026-11-06. This updates the cost and token qualifications in [FINDINGS-2](FINDINGS-2.md), sections B/C. The public Admin API is documented; the personal dashboard and `api2.cursor.sh` RPC are private interfaces. The published Admin fields are strong evidence for the similarly named dashboard fields, but not a formal guarantee of identical semantics across endpoints, plans, or historical versions. No authenticated Cursor API was called for this research. Source examples and the local database check below are not invoice reconciliation.

## Decisions

- Keep `tokenUsage.totalCents / 100` as **Cursor-reported model/token cost**, with its provenance. It is the best reported model-cost value when present, but calling it universally "API-equivalent" or "the amount paid" overstates what is known. For third-party calls it can approximate provider list-rate value; for Auto, Cursor's own models, discounts, or special tiers it is Cursor's meter, not a verifiable direct-provider API bill. Preserve `chargedCents`, `cursorTokenFee`, `kind`, `isChargeable`, `isTokenBasedCall`, and `discountPercentOff` separately.
- In the current documented team API, `chargedCents / 100` is the **event spend meter including any applicable Cursor Token Rate**, and Cursor explicitly says to sum it to reconcile `/teams/spend`. It is not always an incremental out-of-pocket payment: positive `chargedCents` and `isChargeable: true` are observed on an included event. Separate plan consumption, on-demand/prepaid debits, and invoice totals; do not infer a dollar payment solely from either cents field or a boolean.
- For this event schema, sum input, output, cache read, and cache write as separate token buckets. Include plan-included, free/promo, and chargeable partial usage in a **reported token throughput** total when they have valid counts; payment status is not a test for whether tokens were processed. For a separately defined **billable usage** view, use observed billing classification and reconciliation; retain unknowns rather than silently classify them.

## 1. What the cost fields mean

| Field | Evidence and interpretation |
| --- | --- |
| `tokenUsage.totalCents` | The [current team Admin API](https://cursor.com/docs/account/teams/admin-api) calls it **total model cost in cents**. It is present inside optional `tokenUsage`, generally for token-based calls. Divide by 100 for dollars without rounding per event. Under this current contract it is the model component before a separately reported Cursor Token Rate; it need not be the wallet debit. The same docs show a discount field, so do not assume every value is an undiscounted, direct-provider list-price valuation. |
| `chargedCents` | Current docs call this the total event amount charged including eligible token rate, and explicitly prescribe summing it to match `/teams/spend`; works on both token- and request-based plans. This is a **spend/usage allocation** field, not proof the card or prepaid wallet was debited for each included event. An included plan still has a subscription price and may consume an allowance. For actual cash, use the relevant on-demand/prepaid/invoice ledger and reconcile scope, credits, taxes and timing. |
| `cursorTokenFee` | Optional fee in **cents**, separate from model cost. In the docs' example, 20.18232 + 1.18 = 21.36232 cents. A discounted example has 40.167 model cents, 10% discount, 1.18 fee, and 37.33 charged cents (consistent with discounting the model amount before adding fee, rounded); do not impose `chargedCents = totalCents + fee` unconditionally. Absent fee is not proof the historical fee was zero. |
| `requestsCosts` | Request **units**, not cents or dollars. Legacy/request-based allowance measure; the January 2026 [Cursor forum response](https://forum.cursor.com/t/clarification-on-request-billing-calculation/149386) says it is ignored for pricing token-based calls. Never add it to monetary fields. |
| `usageBasedCosts` | Private dashboard display string, e.g. `"$1.21"` or `"-"` for included usage in [observed examples](https://gist.github.com/dmwyatt/1e9359b1862e7cbfe1e754fe4c8db764) and [included event JSON](https://forum.cursor.com/t/safeguard-fallback-to-opus-4-8-is-billed-as-the-model-you-selected-not-as-opus-4-8/172823/6). It is formatted, possibly rounded or sentinel, not a reliable exact cents value or a complete ledger. |
| `isChargeable` | The Admin API calls it whether the event incurs a charge. This is insufficient to infer extra out-of-pocket payment: an actual posted `INCLUDED_IN_BUSINESS` row has `true`, `chargedCents > 0`, and `usageBasedCosts: "-"`; the official illustrative included request-based row has `false` yet positive `chargedCents`. [Source example](https://forum.cursor.com/t/safeguard-fallback-to-opus-4-8-is-billed-as-the-model-you-selected-not-as-opus-4-8/172823/6), [Admin docs](https://cursor.com/docs/account/teams/admin-api). Preserve the distinction; do not universally filter spend or tokens with this flag. |
| `kind` | Billing category, not an exhaustive stable public enum. `INCLUDED_IN_PRO_PLUS`/`INCLUDED_IN_BUSINESS` indicate inclusion in the named plan; usage-based/on-demand labels indicate additional metered usage in the applicable plan; `ERRORED_NOT_CHARGED` says no charge for that event. Public Admin API uses human-readable labels such as `Usage-based` and `Included in Business`; private dashboard exposes enum-like identifiers. Preserve unknown kinds and avoid mapping all non-included kinds to paid. BYOK, promotions, credits and plan transitions require context. |

**Fee conflict:** A January 2026 [forum answer](https://forum.cursor.com/t/clarification-on-request-billing-calculation/149386) says `totalCents` includes a token fee and is charged. This contradicts the current explicit Admin API contract and examples. Its own listed line-item arithmetic is also inconsistent: $0.000078 + $0.152520 + $0.286579 + $0.062617 is approximately $0.501794; adding $0.25 per million across 295,338 tokens gives about $0.57563, not the stated $0.836. We cannot establish whether the older answer reflects a different historical schema, missing charges, or error. Prefer current formal docs for current Admin rows, preserve raw values for historical/private rows, and do not retroactively assert a universal rule. Individual account plans need their own reconciliation.

As of the research date, the [pricing page](https://cursor.com/docs/models-and-pricing) states eligible Teams/Enterprise third-party requests have $0.25 per million input, output and cached tokens, subject to exemptions including Cursor models, Cost mode and low cache-read-price models; individual plans do not pay this rate. Applicability and pricing have changed, so evaluate at the event date rather than backfill today's policy. Even the [token-rate help page](https://prod.cursor.com/help/models-and-usage/token-rate) is less detailed than the current model pricing page about exemptions.

**Concrete included counterexample:** The [published `composer-2.5` private RPC sample](https://github.com/cnwinds/cursor-pulse/blob/master/docs/cursor-usage-api.md) shows `INCLUDED_IN_PRO_PLUS`, `isChargeable: true`, `totalCents: 3.45131`, `chargedCents: 3.45131`, and `usageBasedCosts: "-"`. This contradicts FINDINGS-2's illustrative implication that included events necessarily have `chargedCents: 0`. Another included Business example has a positive separate fee. These are observations, not proof of every account's ledger. The community notes were available in search cache but the GitHub page returned 404 on a fresh fetch; their continued availability and currency are unverified. A third-party [burnrate implementation](https://pkg.go.dev/github.com/andregcab/burnrate@v0.1.3/internal/cursor) explicitly avoids `isChargeable` as its extra-billing filter because included rows may set it true; its own `kind`-based rule is an implementation choice, not an authoritative complete classification.

## 2. Token buckets and inclusion

Cursor forum representative [Mohit Jain](https://forum.cursor.com/t/a-way-to-get-full-observability-on-token-uses/171345/7) explicitly describes `inputTokens` as **uncached**, `cacheReadTokens` as cached input, and `cacheWriteTokens` as input written to cache. The [pricing tables](https://cursor.com/docs/models-and-pricing) and [Tokscale's Cursor normalization](https://github.com/junhoyeo/tokscale/blob/main/crates/tokscale-core/src/sessions/cursor.rs#L129-L235) treat the four as separate price/count buckets. Thus for this endpoint's usual schema:

```
input processed = inputTokens + cacheWriteTokens + cacheReadTokens
total reported tokens = inputTokens + cacheWriteTokens + cacheReadTokens + outputTokens
```

Do **not** subtract cache reads or cache writes from `inputTokens`; that would undercount. This resolves the open question in FINDINGS-2 for the normal Cursor event schema, not every different Cursor SDK/hook/provider schema. A token can be counted in multiple events when context is resent; throughput is not unique text size. Separate reasoning count is not established for these events; do not add a hypothetical reasoning field to output without proving whether it is a subset. Some optional zero-valued fields are omitted by the wire format; absent `tokenUsage` or an unverified missing component should remain unavailable rather than falsely implying complete zero usage.

## 3. Which kinds to count

- **Reported throughput:** include valid reported categories irrespective of `INCLUDED_*`, `USAGE_BASED`/on-demand, free/promo, BYOK, or `isChargeable`, because monetary treatment is different from model processing. If a row explicitly says `ERRORED_NOT_CHARGED` or the older display label `Aborted, Not Charged`, mark it non-billable; whether any nonzero reported counts represent actual processed tokens is not established merely by that label. Keep them separately visible or mark the throughput total's coverage/definition; do not silently equate "not charged" with "zero tokens". A 2025 [user bug report](https://forum.cursor.com/t/aborted-errored-requests-are-being-counted/106462) alleges quota increased for such events, but does not establish correct behavior. A [Cursor representative](https://forum.cursor.com/t/make-the-usage-tab-actually-useful/162933/6) says requests failing to generate a response are not charged; a free label can also be a promotion.
- **Billable/paid usage:** exclude explicit `*_NOT_CHARGED` from a customer-charge view after settlement, and include usage-based/on-demand according to its actual plan classification. Do not exclude all `INCLUDED_*` from throughput or pool consumption, even if excluded from incremental out-of-pocket charges. BYOK may incur direct-provider charges and potentially a Cursor fee; those are different ledgers. Unknown or contradictory kinds/flags need an unknown bucket, not a fabricated zero or paid value.
- **Partial/aborted:** do not exclude a row simply because a run was stopped. Cursor staff [said on October 22, 2025](https://forum.cursor.com/t/aborted-errored-requests-are-being-charged/137676/15) that charging for partial stopped requests was an intentional change. An old explicit `Aborted, Not Charged` label and a currently metered stopped request are different cases. Error rows can be reconciled after first appearing; preserve/re-fetch corrections rather than assuming the first state is final.

No primary source located establishes a complete list of private enum spellings, or guarantees all `ABORTED_*`/`ERRORED_*` kinds carry no token usage. Never make prefix-only exclusions a universal rule.

## 4. Numeric representation and missing token records

`totalCents` can be fractional: the [public forum event](https://forum.cursor.com/t/cursortokens-app-track-actual-costs-after-sept-15-pricing/138059) reports `4.457141876220703` cents; official docs show `20.18232`. Some values exhibit floating-point representation artifacts. Retain full precision, sum then round for display, and distinguish missing/invalid from explicit zero. Official Admin docs specify JSON **number**; [Tokscale's parser](https://github.com/junhoyeo/tokscale/blob/main/crates/tokscale-core/src/sessions/cursor.rs#L129-L235) intentionally accepts numeric strings for both cents fields. That is useful defensive compatibility, **not independent proof that Cursor has actually emitted `totalCents` as a string**. Accept a finite, nonnegative numeric string if desired, retaining its units/provenance; do not parse `usageBasedCosts` dollars as cents.

The field's spend-meter meaning still does not prove incremental payment for that included event. A token-only importer drops such cost-bearing rows and cannot claim complete event spend or zero tokens for them. Conversely, presence of `tokenUsage` does not prove a cash debit.

## 5. Published prices and missing `totalCents`

[Cursor Models & Pricing](https://cursor.com/docs/models-and-pricing) publishes per-million input, cache-write, cache-read and output rates for current Cursor and third-party models, with speed/long-context distinctions. At this research date examples include Composer 2.5 standard $0.50 input / $0.20 cache read / $2.50 output and Grok 4.7 standard $2 / $0.50 / $6. Those rates are **not** a mapping from `grok-bot-default` to a specific model, mode and time. A dash in a price table is not automatically proof of zero cost. Historic [Cursor pricing](https://docs.cursor.com/account/pricing) gave Auto $1.25 input, $0.25 cached input, $6 output per million starting at the relevant 2025 renewal, while current Auto/Router has mode- and plan-specific routing and billing rules. Do not apply today's rates retrospectively.

`claude-4.5-sonnet-thinking` is plausibly a named Claude variant but name alone does not prove exact historical tier, discount, regional uplift, context threshold, fast mode, fallback route, or underlying model. `auto` is a routing/billing mode and can have a special rate or model-specific rate depending on date and plan. `grok-bot-default` is an alias and `composer-1` is historical; neither has a verified exact rate mapping for all events from the sources reviewed. Even a labeled model can hide a route: a [user's reported fallback](https://forum.cursor.com/t/safeguard-fallback-to-opus-4-8-is-billed-as-the-model-you-selected-not-as-opus-4-8/172823) illustrates why ID-to-provider identity is not guaranteed. Treat it as an unverified user report, not a general contract.

When a historical, effective-dated Cursor rate card and exact variant/tier are known, a **labeled estimate**, excluding or separately including eligible fees, can be calculated as `(input*r_in + write*r_write + read*r_read + output*r_out) / 1_000_000` dollars. Store its date, rates, assumptions, and coverage. Otherwise leave cost unknown; never overwrite reported `totalCents`, and never substitute a guessed current rate as exact historical or actual billed cost.

## 6. Endpoints and coverage

| Surface | Useful fields and limitations |
| --- | --- |
| `POST https://cursor.com/api/dashboard/get-filtered-usage-events` | Existing private session-cookie route, `usageEventsDisplay` and `totalUsageEventsCount`. Per-event token breakdown, `totalCents`, often `chargedCents`, fee, flags, display string and kind. It already supplies the useful per-event figures when present. It is undocumented and field presence varies. See [Tokscale importer](https://github.com/junhoyeo/tokscale/blob/main/crates/tokscale-cli/src/cursor.rs) and [dashboard observations](https://gist.github.com/dmwyatt/1e9359b1862e7cbfe1e754fe4c8db764). |
| `POST https://api2.cursor.sh/aiserver.v1.DashboardService/GetFilteredUsageEvents` | Private Connect JSON RPC, Bearer access token plus `Connect-Protocol-Version: 1`; [community notes](https://github.com/cnwinds/cursor-pulse/blob/master/docs/cursor-usage-api.md) show `startDate`/`endDate` millisecond strings, 1-based `page`, `pageSize`, and the same `usageEventsDisplay` shape including cents/fee/flags. It is an alternative authentication/transport, **not demonstrated to give more precise or more complete per-event costs**. No live parity test here. |
| `POST https://cursor.com/api/dashboard/get-aggregated-usage-events` | Private aggregate, **not per-event**. A [published example](https://forum.cursor.com/t/update-the-docs-and-dashboard-to-tell-us-exactly-whatbwe-ae-paying-for/152538/6) has `aggregations[]` with `modelIntent`, token counts encoded as strings, `totalCents`, `tier`; top-level `totalInputTokens`, `totalOutputTokens`, `totalCacheWriteTokens`, `totalCacheReadTokens`, `totalCostCents`. Useful as a scope-matched cross-check, but fields are subject to omission, delayed aggregation, filtering and corrections. Its aggregate `totalCents` cannot establish which event/ledger or fee components it contains. |
| `POST https://api2.cursor.sh/aiserver.v1.DashboardService/GetAggregatedUsageEvents` | [Community-documented RPC](https://github.com/cnwinds/cursor-pulse/blob/master/docs/cursor-usage-api.md) returns per-model `aggregations` with the same categories, `totalCents`, `tier`; supports date/user/team filters. Its reported default current-cycle behavior is an observation, not a contract; authenticate and compare account, dates, filters and completeness before reconciliation. |
| `POST https://api.cursor.com/teams/filtered-usage-events` | **Documented** Admin API, separately provisioned team admin key (Basic auth), `usageEvents` rather than `usageEventsDisplay`, pagination and period metadata, token and charge fields. Cursor says hourly aggregation, poll at most hourly, 60 requests/min/team, and sum `chargedCents` against `/teams/spend`. Team-scoped with admin permissions; it is not a substitute for arbitrary personal accounts or necessarily a cash invoice. [Official docs](https://cursor.com/docs/account/teams/admin-api). The [organization endpoint](https://cursor.com/docs/account/organizations/organization-admin-api) adds `teamId` and reconciles to pooled team usage. |

An aggregate cannot reconstruct individual costs. Preserve event fields, pagination completeness and account/time scope from FINDINGS-2; refreshing an overlap may miss older corrections, so allow wider reconciliation. No better universally available personal endpoint proving exact cash per event was found.

## Local sanity check

Read-only SQLite query on TokenHell's `events`, restricted to the requested `provider='cursor'` columns, found 168 rows, all `grok-bot-default`: input 1,546,800; output 64,184; cache read 3,998,930; cache write 76,706; all 168 have `cost_reported`, summing to $11.429327. These stored numbers are an ingestion sanity check, not independent evidence of provider semantics, raw event kinds, exact model mapping, completeness, fee, paid amount or invoice reconciliation. No credentials, `limits`, `kv`, raw session contents, or authenticated API responses were read.
