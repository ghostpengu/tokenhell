# Cursor CLI / Grok real-time usage research

Research date: 2026-11-06. **Verified** distinguishes direct inspection or an identified source's stated behavior from **inferred** implications. No Cursor settings or files were changed, and no model request was initiated. Authenticated dashboard probes were read-only and inspected only status, key names, shapes and row counts. Findings are specific to this installation/account unless stated otherwise.

## Key result

**Verified (installed code); live Grok behavior untested:** Interactive Cursor CLI has a promising per-**turn** token source: the `stop` hook. In `~/.local/share/cursor-agent/versions/2026.11.05-86047df/1706.index.js` (minified, byte offsets ~880000–881800 and ~888900–889500), the interactive path takes usage from `turnEnded` and passes `conversation_id`, `generation_id`, `model`, `status`, `input_tokens`, `output_tokens`, `cache_read_tokens`, and `cache_write_tokens` to `stop`. The counts are optional. The same code passes them to `afterAgentResponse` (~offset 700), and invokes `stop` for completed, aborted, and error paths. One user turn can contain multiple model calls; this is a turn aggregate, not necessarily a per-API-request record. The hook runs near turn completion, so expected delivery is local and immediate apart from hook scheduling; **actual latency and availability on Grok 4.7 are unmeasured**.

**Verified (independent report, different model/version):** A [prototype report](https://github.com/Astra20230303/omnigent-handbook/blob/main/docs/cursor-native-cost-tracking.md#2-why-it-was-thought-impossible-and-what-changed) describes a real interactive CLI 2026.06.24 `stop` payload with all four counts for Claude, but says its headless run did not fire hooks. It is not evidence of this account's Grok payload. Cursor's [hooks documentation](https://cursor.com/docs/hooks) documents user and project hook configuration and Agent lifecycle events; field details may change.

**Verified (installed code):** Hook `input_tokens` is **inclusive** of cache reads and writes: the same CLI subtracts them for its UI. For TokenHell's disjoint buckets, compute `uncached_input = max(input_tokens - cache_read_tokens - cache_write_tokens, 0)`; preserve raw fields and detect inconsistent/missing counts rather than silently inventing zeros. Use one hook (`stop`), not both hooks, and deduplicate by conversation and generation ID. The same version's headless JSON usage is already normalized to uncached input; do not subtract twice. Source: same bundle offsets ~570524, ~881500 and ~889200. **Inferred:** compare captures with dashboard rows when available to verify semantics, abort behavior, subagents and billing coverage before treating either feed as authoritative.

## Other potential sources

- **Headless CLI — verified in installed code, not executed:** `agent -p --output-format stream-json` emits `type: usage`, `subtype: model_call` with `model_call_id` and a `usage` object when `modelCallCompleted` arrives, and a terminal `result.usage` if usage was supplied. Fields include `inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheWriteTokens`, and optional `reasoningTokens`; input is normalized as above. The terminal result is a turn/run aggregate, so do not add it to the per-call events. A missing final result on errors or cancellation and missing usage are possible. Source: `1706.index.js` offsets ~570524, ~576118–577200, ~583981–584600. **Inferred:** a wrapper consuming stdout can record per-call counts near completion but cannot observe already-running interactive sessions. No live Grok or precise latency test was run. [Cursor SDK documentation](https://cursor.com/docs/sdk/typescript) independently states that usage can be absent and that reasoning is a subset of output, not another additive bucket.
- **Dashboard — verified for this account, 2026-11-06:** `POST /api/dashboard/get-filtered-usage-events` returned HTTP 200 with an empty object for Oct 14 onward; `POST /api/dashboard/get-aggregated-usage-events` returned HTTP 200 with only `startDate` for that window. `POST /api/dashboard/get-current-period-usage` and `GET /api/usage-summary` returned aggregate period/plan structures, not observed per-request token fields; `POST /api/dashboard/get-sand-usage-status` returned numeric `usagePercent` and reset/availability fields, with no token-count fields. The brief reports older event rows through Oct 13. Request shapes and existing parsing: [cursor.rs](../crates/th-core/src/limits/cursor.rs#L112), [event sync](../crates/th-core/src/limits/cursor.rs#L213); aggregation endpoint shape: [independent client](https://github.com/devilcoolyue/cursor-panel/blob/main/cursor_dashboard/client.py). Empty results do not prove no other endpoint exists. API2 dashboard RPC and Grok's own dashboard were not authenticated or tested.
- **Server lag — unmeasured:** No controlled new Grok or normal-model request was made. Cursor [claims real-time dashboard usage for legacy plans](https://prod.cursor.com/help/models-and-usage/usage-limits); a [Cursor forum response](https://forum.cursor.com/t/cost-information-in-cursor-cli-headless-mode/164583/7) says team Admin API data is aggregated hourly. Those statements do not establish the latency of this private filtered-events endpoint or this X plan. [Admin API docs](https://docs.cursor.com/en/account/teams/admin-api) describe per-event `tokenUsage` for eligible team accounts, not availability for this individual Grok account.
- **Local stores — verified scan, limited coverage:** SQLite online backups into memory were used for the inspected databases; no transcript or secrets were printed. Two of three CLI `~/.cursor/chats/**/store.db` files were readable via backup and had `blobs`/`meta`; one failed to open. Literal searches cannot rule out numeric protobuf fields: see the [store format investigation](https://harnessnotes.com/session-transcripts/format?harness=cursor-agent). The AI tracking DB schema contains code hashes, file content and conversation summaries, no token-usage columns (`~/.cursor/ai-tracking/ai-code-tracking.db`). CLI config and Statsig cache had no structured usage record established. Desktop `~/Library/Application Support/Cursor/User/globalStorage/state.vscdb`, `cursorDiskKV` `bubbleId:` JSON, contained 1,656 `tokenCount.inputTokens` / `outputTokens` pairs; all inspected values were zero. These are not a usable historical usage feed on this machine. Workspace DB scans found no literal usage-field matches. Logs/project transcripts were not exhaustively decoded; absence of a string is not proof of absence of protobuf data.
- **SDK — verified documentation, different integration:** [Cursor SDK `getUsage()`](https://cursor.com/docs/sdk/typescript) reports billed tokens/cost per local turn or cloud run where enabled; local access is rolling out and can return `403 feature_unavailable`. SDK live `run.usage` is optional. **Inferred:** useful for SDK-owned agents, not established as a way to query arbitrary existing CLI sessions or this Grok plan.

## Weekly percentage

**Verified:** The status response has `usagePercent` and a reset timestamp, and [Cursor says](https://prod.cursor.com/help/models-and-usage/usage-limits) the X subscription has a weekly pool shared by Cursor, Grok Bot and Grok apps; model choice affects consumption. **Unverified:** whether each request changes the displayed percentage, rounding granularity, propagation delay, or whether a percentage delta is attributable to a single Cursor call. No denominator, pricing weights or per-model token mix was exposed by the tested status response. **Inferred:** do not convert the percent into token counts or dollars, or attribute a change exclusively to the local CLI. Show it as a shared weekly allowance with reset and last-refresh time.

## Recommendation, ranked

1. **Interactive CLI:** Offer an opt-in, nonblocking `stop` hook that writes only normalized usage metadata to a TokenHell-owned append-only log. Preserve existing hooks and configuration, avoid recording prompt/response text, return `{}` promptly, deduplicate generation IDs, and handle absent or partial usage. Hook installation would change Cursor configuration and is a future implementation step, not part of this research. Validate live using a small Grok turn, including whether reported counts exist and how cached input, interruption, concurrent sessions and subagents behave.
2. **Headless CLI:** For users who opt into a wrapper, capture `model_call` usage from stream JSON; use the final aggregate as a fallback or reconciliation, never both as additive records. Preserve stdout and handle errors/partial output. This measures wrapped runs only.
3. **Account-wide truth:** Keep the weekly shared percentage and reset from sand status. Poll with backoff, respect rate limits and display freshness; do not claim a particular update interval without measurement. Keep filtered-event sync for eligible normal models/accounts and historical reconciliation; avoid double-counting matched hook events, and retain local-only entries where no matching server event exists.
4. **Do not rely on** desktop zero counts, local context-window occupancy, or percentage-to-token conversion. Consider SDK/Admin APIs only for accounts and execution modes where access and coverage are verified.

**Next validation:** With a user's normal interactive Grok turn, timestamp hook receipt and sample sand/filtered/aggregate responses before and after (then at increasing intervals), without logging prompts or credentials. Repeat with a normal model on an eligible account. Compare per-turn hook totals with per-model-call stream events and later dashboard records, accounting for inclusive cache input and overlapping sources. Until measured, there is no defensible seconds/minutes lag or per-request percentage guarantee.
